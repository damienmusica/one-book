## 물량 트랙 — 완성의 정의와 본보기

각 트랙은 **본보기 하나가 이미 레포에 있다.** 새로 발명하지 말고 본보기의
수준을 복제하라. 속도를 위해 수준을 낮추는 것은 완성이 아니다.

1. **작품 세계 확장** — 다음 대상: 소세키 6작품 · 타고르 6작품(착륙 가능 작가
   먼저). 본보기: 카프카 5작품의 `world` 필드(`data/works/early-west-a.json`)와
   출처 묶음(`data/sources/kafka-world.json`). 완성 = 여는 문장을 **실제로 연
   페이지에서 축자 확인**(PD 원문 — Wikisource·Aozora Bunko 등, URL·accessedAt
   기록), 한국어는 자체 번역으로 표시, 판본·유고는 출처와 함께, 스키마·검증
   통과. 기존 한국어 번역서의 문장을 가져오는 것은 금지다(저작물).
2. **관계 앵커 큐레이션** — 카프카 10행이 본보기(`data/relations/*.json` 의
   `anchors`). 완성 = 나머지 관계 중 **요약문이 이미 지목하는** 책·연도만 앵커로
   승격(새 조사 0, 요약에 없는 사실 금지), 검증 통과(당사자의 실재 작품만).
   요약이 아무것도 지목하지 않으면 앵커를 만들지 않는다 — 실이 이름에 닿는
   것도 정직한 독해다.
3. **실물 자산 파도** — 본보기: 서명 파도(`art-r10/stage-signatures.mjs` →
   `build-art-assets.py`, 원장 `docs/art-direction-r10.md`). 남은 것: 보류 6건의
   인간 재검(울프 크롭·CC BY-SA 판단), P18 기록 사진 파도(99인 가용 — 파일별
   권리 확인이 병목), 육필 지각 파도. 완성 = 파일마다 프로비넌스 행, 정책 보류
   (생존 작가·공유동일조건)는 코드가 아니라 기록으로 남김, 출하 행성 앱의 자산
   집합 불변(매니페스트 버킷 분리 원칙 유지), 관련 계약 통과. 수집 우선순위는
   편집 균형(지역·언어 공백 우선, 정전 순 금지 — 테제 §⑤).
4. **다국어 정합** — `node-translations` 계열과 새 표면 문자열(회랑 각인·시트
   라벨)의 en 로케일 정합은 아직 손대지 않았다. 기존 로케일 체계 안의 정합은
   자체 판단으로 진행한다(새 로케일 추가만 범위 확장이다).

   *2026-08-28 실측 — 이 항목은 "정합"이 아니다.* 성계 모듈에는 **로케일 배선이
   아예 없다.** 진입점이 `<UniverseApp dataset={dataset} />` 로 로케일을 받지
   않고(`src/universe/main.tsx`), 행성 앱이 쓰는 `?l=<locale>`(`state/url.ts`)은
   성계에서 아무 일도 하지 않는다. 반면 행성 앱은 `state.locale` 로
   `documentElement.lang` 까지 맞춘다(`components/App.tsx`). 즉 **성계는 구조상
   한국어 전용**이고, 표면 문자열 약 40개(회랑 각인 4 · 시트 라벨 5 ·
   `OrbitCard` ~21 · `UniverseApp` ~19)가 전부 한국어 리터럴이다.

   그래서 이 트랙의 실체는 문자열 치환이 아니라 **로케일 상태를 성계에 들이는
   기능**이다(상태 + prop 배선 + 표면 문자열 사전 + `data/translations/<locale>/`
   스키마 확장 여부 판단). 크기와 성격이 다른 일이므로 물량 트랙에서 떼어
   따로 스코핑한다. 그래프 토폴로지 불변식과는 무관함을 확인했다 — 이 문자열들은
   전부 표시용이고 ID·엣지 조회에 쓰이지 않는다. 다만 `scene.ts` 의
   `author.names.ko` **직접 참조**는 로케일 분기가 아니라 필드 고정이라, 배선이
   들어올 때 없는 번역을 지어내지 않는 폴백 규칙이 함께 필요하다.

  가용 최강 티어).

## 게이트 명령

```bash
npm run typecheck && npm run validate:data && npm test
node art-r11/verify-journey.mjs        # 넓은 화면 여정 계약 (dist 빌드 후)
npm run universe:flight                # 카메라 주권 — 조준·추력·걷기 (한 판 60초)
npm run universe:mobile                # 손안의 계약 — 390×664, 손가락 입력
npm run universe:reproduce             # 한 명령 전체 게이트 + 리포트
npm run universe:mutation-sweep        # 계약의 이빨 측정 (트리 잠금)
```

새 화면 문법을 더하면 **넓은 화면과 손안 양쪽에** 계약을 단다. 한쪽만 달면
다른 쪽이 조용히 깨진 채로 게이트를 통과한다 — 그것이 R12-d 의 출발점이었다.

**변이 스윕은 트리를 잠근다 — 그리고 죽여도 잠긴 채로 남을 수 있다.** 2026-08-25
에 3초짜리 정찰 실행이 파이프 뒤에서 살아남아 35분 동안 트리와 `dist` 를
갈아엎었고, 그동안 찍은 프레임과 돌린 계약이 전부 변이된 빌드를 측정했다
(계약 하나가 부호 반전으로 보이던 것이 원인 추적을 40분 잡아먹었다). 이제
스윕은 변이 전에 원본을 `.mutation-sweep-backup/` 에 떨어뜨리고, 그 디렉토리가
남아 있으면 **다음 실행을 거부한다**:

```bash
python3 scripts/universe-mutation-sweep.py --repair   # 남은 사본에서 되돌린다
python3 scripts/universe-mutation-sweep.py --lane browser --only "주권"  # 새 기제만
```

스윕은 `nohup … > 로그 &` 로 띄우고 **끝날 때까지 편집도 빌드도 계약 실행도
하지 않는다.** 중단해야 하면 프로세스 그룹째 SIGINT 를 보내고 살아 있는지
`ps` 로 확인한다.

**이 규율은 2026-08-28 에 세 번째로 깨졌다.** 스윕을 띄운 직후 같은 트리에서
유닛·여정·손안 레인을 돌렸다 — 그때 나온 숫자는 변이된 빌드를 쟀을 수 있으므로
버리고 다시 돌렸다. 매번 같은 방식으로 깨진다: 스윕은 **오래 걸리고 조용해서**
그 사이에 다른 일을 하고 싶어진다. 스윕을 띄우는 순간 **트리는 내 것이 아니다** —
그동안 할 수 있는 일은 스윕이 건드리지 않는 문서 편집뿐이고, 게이트 숫자는
스윕이 끝난 **뒤에** 잰 것만 유효하다.

`pgrep -f "universe-mutation-sweep"` 은 **자기 자신을 매칭한다** — 그 문자열이
대기 루프의 명령줄에도 있기 때문이다. 대기 루프가 자기를 보고 "아직 돈다"고
말하는 것을 스윕이 안 끝난 것으로 읽지 말 것(`pgrep -f "scripts/universe-…"`
처럼 경로로 좁힌다).

## R12-g 별에도 크기가 있다 (2026-08-27, 완료)

CPO 지적에서 나왔다. 별의 화면 지름은 이제 **광휘 바닥과 실제 원반 중 큰
쪽**이다(`grammar.ts` `starDiameterPx`). 이전 판에서 크기가 자라는 유일한 길은
구로 분해되는 것이었고 분해는 `isLandable` 이 막으므로, **100인 중 97명의 별은
아무리 다가가도 같은 점**이었다(실측: 2189 → 379 단위 동안 발광 폭 2~3px 고정).

- 화면 지름을 정하는 곳은 프레임 루프 **한 곳**이다 — 거리를 아는 것이 거기뿐.
  `refreshStars` 는 거리 무관한 광휘만 `baseGlare` 에 적는다.
- `nearPx` 계측은 규칙을 재계산하지 않고 **셰이더에 넘어간 값을 읽는다.**
- 렌즈가 옮긴 압축 사본은 **상징이지 천체가 아니므로** 원반을 주지 않는다.
- 넘겨받을 구가 없는 별에는 상한이 있다(`STAR_MAX_PX = 128`).
- 계약 8건(유닛 5 · 비행 3) · 변이 4건 신설 → 스윕 killed 5 · survived 0.

**먼 하늘은 건드리지 않았다** — 프레임 29장 diff 에서 `0sky-*` · `*-1sky` ·
`5personal` · `6year-*` · `8lens-linked` 가 다른 픽셀 0개.

### 프레임 diff 는 상태 단언보다 강하다

"먼 하늘이 그대로다"를 증명한 것은 프로브가 아니라 **이전 프레임과의 픽셀
diff** 다. 같은 레시피를 다음 라운드에서도 쓴다: 변경 전 `art-r11/frames/` 를
어딘가로 복사해 두고, `capture-universe.mjs` 를 다시 돌린 뒤 두 디렉토리를
픽셀 단위로 비교한다. 상태 단언이 초록인 채 렌즈가 한 릴리스 내내 엉뚱한 자리에
렌더된 적이 있다 — **시각 게이트는 프레임 diff 로 잰다.**

## 작품 세계 — 남은 칸 (2026-08-27 기준, 결정 (119) 형식)

소세키 6작품은 전부 채웠다. 타고르는 **6 중 3**이다. 나머지 셋이 남은 이유는
자료가 아니라 **검증 가능성**이고, 각각 막힌 지점이 다르다.

- `rabindranath-tagore--ghare-baire` 는 여는 문장조차 없다. 벵골어 위키문헌에
  『ঘরে বাইরে』 전사가 없고, archive.org 의 1916년 스캔
  (`in.ernet.dli.2015.453563`)은 **텍스트 층이 비어 있다**(내려받은 djvu.txt 가
  0바이트). 다른 PD 전사를 찾기 전에는 기입하지 않는다 — 벵골어 OCR 추정을
  '원문 그대로'로 적을 수는 없다.
- `rabindranath-tagore--gora` 는 여는 문장을 확인했지만
  (「শ্রাবণ মাসের সকালবেলায়…」) 저본이 **1961년 인쇄본**이고(위키데이터
  Q96146840), 1910년 초판의 발행처를 어떤 열람 가능한 출처에서도 찾지 못했다.
  스키마는 판본에 발행처와 발행지를 요구하므로 `world` 를 쓸 수 없다.
- `rabindranath-tagore--kabuliwala` 도 여는 문장은 확인했지만
  (「আমার পাঁচ বছর বয়সের ছোটো মেয়ে মিনি…」) 저본이 **1950년 비슈바바라티

## 작품 하나를 더하면 무엇이 따라오는가 (2026-08-28, 값을 치르고 배움)

`franz-kafka--der-verschollene` 한 편을 넣자 검증기가 파급 둘을 잡았고, 그중
하나는 **함정**이었다.

**① en 번역 커버리지** — 모든 작품은 `data/translations/en/works/` 에 항목이
있어야 한다. 쉬운 파급.

**② 영토 재베이크 — 여기에 함정이 있었다.** 검증기는 `cities[...] towns do not
match the author's works — re-bake territory` 라고 시킨다. 그런데 시키는 대로
`npm run terrain:plate -- --freeze` 를 돌리면 **다른 행성이 덮어써진다**:
동결본은 `R0 0.085 · tau 0.62 · warp 0.12` 로 구워졌는데 생성기의
`DEFAULT_PARAMS` 는 `0.11 · 0.5 · 0.1` 이다. 실측 결과 `landFraction` 이
**0.3229 → 0.6675** 로 두 배가 되고 소유권이 전면 재배치됐다 — 작품 한 편을
더한 사람이 대륙을 갈아엎게 되는 것이다.

동결 파라미터로 다시 구우면 **해안·수계·국경·소유권이 전부 동일**하고
(소유권 셀 205,393개 중 **0개** 변화, 영토 지분 100인 전원 불변 — 면적 가중치는
작품 수가 아니라 tier×관계차수이기 때문이다), 바뀌는 것은 `cities` 하나다.
카프카 도시의 마을이 5 → 6 이 된다.

**그래서 `--freeze` 에 가드를 넣었다**: 기존 동결본의 `params` 와 다르면 거부하고
**정확한 명령을 출력한다**. 새 행성을 의도적으로 구울 때만 `--force-params` 로
뚫린다. 이 가드는 제품 불변식이 아니라 **개발자 안전난간**이라 계약 대신
시연으로 잰다 — 기본 파라미터로 실행해 거부와 안내 문구가 나오는 것을 확인했다.

**정확한 재베이크 명령 (외워 두지 말고 가드가 알려주게 둘 것):**
```
npm run terrain:plate -- --freeze --R0 0.085 --tau 0.62 --warp 0.12
```

**하네스 상수도 따라온다**: `verify-journey.mjs` 의 작가 표가 작품 수를
하드코딩한다(카프카 5 → 6). 표지 수(4)와 입문 경로(3편)는 그대로다 — 미완
유고작은 첫 독서가 아니므로 `readingOrder` 에 넣지 않았다.

### 왜 『실종자』였나

상한이 6편이므로 카프카에 넣을 수 있는 것은 **한 편뿐**이었다. 후보 넷의 자료를
전부 확인한 뒤(『관찰』1912 · 『단식 광대』1924 · 『실종자』1927 · 『아버지에게
드리는 편지』1952 — 넷 다 여는 문장과 초판 서지 확인됨) 『실종자』를 골랐다.
코퍼스가 카프카 장편 **3편 중 2편**만 갖고 있던 것이 가장 눈에 띄는 구멍이었기
때문이고, 회랑의 가장 큰 초기 공백(1927–35, 9칸)에 착지하기 때문이다.

여는 문장의 저본이 특히 좋다: 이 소설의 첫 장은 카프카 **생전인 1913년**에
『화부』로 따로 나왔고(Kurt Wolff, Leipzig · 「Der Jüngste Tag」 3권), 그 초판
스캔이 de.wikisource 에 **교정 완료** 상태로 있다. 그래서 여는 문장은 유고
편집자의 손을 거친 판본이 아니라 **카프카가 직접 인쇄에 넘긴 지면**에서 읽었다.
소설의 첫 문장이 소설보다 14년 먼저 인쇄돼 있었던 셈이다.

## 통합 내부 심사 (2026-08-28) — 결함 6건, 그중 blocking 1

R12-g + 물량 두 웨이브 뒤에 빌드를 다섯 축으로 적대 심사했다(회랑 걷기 · 뷰포트 ·

### 이 라운드가 배운 것 — 계약이 도달할 수 없는 상태를 재고 있었다

blocking 결함이 지금까지 빠져나간 이유가 핵심이다. **두 계약이 각각 초록이었다**:
「착륙 뒤 초점이 착륙 패널에 있다」와 「회랑에서 화살표·+ 가 걷는다」. 그런데
두 번째 계약이 키 입력 직전마다 `canvas.focus()` 를 **강제**해, 첫 번째 계약이
만든 바로 그 상태를 우회했다. 사용자가 만들 수 없는 자리를 손으로 만들어 놓고
그 위에서 잰 것이다.

**규칙(헌법에 신설):** 계약의 준비 코드가 `focus()`·`click()`·상태 주입으로
만든 자리는 **사용자가 그 경로로 도달하는 자리와 같아야 한다.**

  못한다. 가드를 지워도 아무것도 안 죽었다. **별의 NDC 좌표로 바꾸고 대조군을
  붙였다**: 같은 키가 검색창 안에서는 움직이지 않고 밖에서는 움직인다

빈 하늘에 설명이 뜨는 것은 이 제품의 어투가 아니고, 없는 문제에 크롬을 다는
것은 이 레포가 금지한 종류의 방어이기 때문이다. 현재 단서는 셋뿐이다:
빈 하늘의 `grab` 커서, 휠을 굴렸을 때 즉시 일어나는 전진, 그리고 손끝의 핀치.

**관찰 지시**: 아무 안내 없이 `/universe` 를 열어 주고, ① 첫 60초 안에 카메라를
스스로 움직이는가 ② 무엇을 먼저 시도하는가(드래그/휠/탭) ③ 별에 다가갈 수
있다는 것을 언제 깨닫는가를 기록한다. 셋 중 ①이 3인 중 2인 이하이면 그때
단서를 더한다 — **관찰 전에 붙이지 않는다.**

## 창의가 허용되는 곳

회랑의 연출 상수(빛·안개·잉크·카메라 미세값), 시트·각인의 문장, 자산 파도의
순서와 묶음, 조사 경로 — 전부 네 판단이다. 단 **화면 문법의 의미**(무엇이
무엇을 뜻하는가)를 바꾸는 순간 그것은 창의가 아니라 개정이고, 개정은 실측
(프레임·계약·변이)을 근거로 CTO 가 판정해 결정 로그에 남긴다. 판단이 막히면
실측을 만들어라 — 이 레포의 모든 좋은 결정
뒤에는 스크린샷·계약·변이 중 하나가 있다.
